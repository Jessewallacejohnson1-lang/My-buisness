# CORRECTNESS — full detail

## [1] A REST-layer 401 (server-revoked/rejected token) never invalidates AuthStore's session or forces re-login
- **CONFIRMED** sev=medium  `Hygge/Backend/SupabaseHTTP.swift:65`  domain=auth-net
- Description: AuthStore's proactive refresh (validAccessToken()) only ever looks at the *local* clock via Session.isExpired (expiresAt - 60s). It never learns that a token was rejected by the server for a REST/PostgREST call. SupabaseHTTP.rest() (line 65-71) simply throws a SupabaseError(status: 401) on any non-2xx response and returns — nothing wires that failure back into AuthStore.session or AuthStore.signOut(). The 'hard failure clears the session and routes back to Login' behavior described in CLAUDE.md and implemented in AuthStore.refresh()/isTokenRejected() only fires when the GoTrue *refresh-token* grant itself is rejected (AuthStore.swift lines 108-149) — it is never triggered by an access-token being rejected on an ordinary CommunityAPI/ProfileAPI call.
- Failure: User's GoTrue session is revoked server-side while the locally cached Session still has expiresAt > now + 60s (e.g., user hit 'sign out other devices' from another client, an admin revoked sessions, or the JWT secret was rotated). session.isExpired is false, so validAccessToken() returns the (now-dead) access token without refreshing. The next CommunityAPI call (e.g. CommunityAPI.swift addEvent/rsvp calls at lines 105/200/226/303/377) sends that token to PostgREST/GoTrue, which returns a real 401. SupabaseHTTP.rest() throws SupabaseError(status: 401); the caller (e.g. AddModel.swift:123, QuickAddSheet.swift:162) just shows a generic 'Couldn't post — try again.' AuthStore.session is untouched, so isExpired stays false and every subsequent action (RSVP, add event, quest completion, profile edit) keeps re-sending the same dead token and keeps failing with the same generic message — the user is never routed back to LoginView and has no way to recover except manually finding a sign-out control.
- Fix: Have CommunityAPI/ProfileAPI (or a thin wrapper around SupabaseHTTP.rest) inspect a thrown SupabaseError's status; on 401 (and ideally on GoTrue-style invalid-token codes), invalidate AuthStore's session (e.g., an AuthStore method that clears session/Keychain the same way a rejected refresh does) so RootView's auth gate routes back to Login instead of leaving the user stuck retrying a dead token indefinitely.

## [2] Stale join()/receiveLoop() Task from a cancelled connection attempt is never cancellation-checked, so a background→foreground cycle can spin up a duplicate receive loop on the new socket and double-count reconnect backoff
- **CONFIRMED** sev=low  `Hygge/Backend/RealtimeClient.swift:118`  domain=realtime
- Description: openSocket() (lines 102-114) spawns `receiveTask = Task { await self?.join(); await self?.receiveLoop() }`. `join()` (118-130) awaits `tokenProvider()` (MapModel.freshToken() -> AuthStore.validAccessToken(), a genuine network/coalesced-refresh call) before sending phx_join, but never checks `Task.isCancelled` or the actor's `stopped` flag before or after that await. `receiveLoop()`'s only cancellation guard (line 169: `guard !stopped, let socket else { return }`) reads the *current* instance-level `stopped`/`socket` properties at call time, not any state captured/pinned to the specific socket generation that spawned it. `teardown()` (92-98) only calls `.cancel()` on the Task handle (cooperative — does not abort in-flight `await`s) and then nils the `receiveTask` property, so the actual suspended Task object keeps running to completion regardless.

MapModel drives exactly the vulnerable pattern via scenePhase (SJMapView.swift ~160-163 -> MapModel.onBackground()/onForeground(), MapModel.swift 83-95): backgrounding calls `realtime?.stop()` on the *same, retained* RealtimeClient instance (it is not nilled — only MapModel.stop() does that), and foregrounding calls `realtime?.start()` on that same instance, which is exactly the reused-instance case where a stale Task's weak-self resolves against live, current state rather than a dead/deallocated object.
- Failure: 1) User opens the Map tab; MapModel.start() -> subscribe() -> RealtimeClient.start() -> openSocket() creates socket A + receiveTask A, whose join() is suspended awaiting tokenProvider() (e.g. a slow network or an in-flight coalesced token refresh). 2) Before that await resolves, the app is backgrounded (phone call, notification swipe, lock) -> scenePhase .background -> MapModel.onBackground() -> realtime.stop() -> stopped=true, teardown() cancels receiveTask A (cooperative only) and nils socket (socket A closed). 3) User immediately returns -> scenePhase .active -> MapModel.onForeground() -> subscribe() (realtime already non-nil, reused) -> RealtimeClient.start() -> stopped is true so it proceeds -> openSocket() #2 creates socket B + a NEW receiveTask B (its own join()->receiveLoop() on socket B). 4) Task A's still-pending join() now resolves its token fetch, and — never having checked cancellation — calls send(event:"phx_join", ...) which reads the *current* `self.socket` (socket B) and sends a redundant join over it, then calls `receiveLoop()`, whose guard reads current `stopped`(false)/`socket`(B, non-nil) and passes, so Task A now also loops `socket.receive()` on socket B concurrently with Task B's own loop. 5) On the next disconnect of socket B, both loops' `catch` blocks independently call scheduleReconnect() (167-182, 226-237), each doing its own teardown()+`reconnectAttempts += 1`, inflating the backoff counter twice per actual disconnect and racing to overwrite `reconnectTask`/`socket`, so the documented capped-backoff cadence (2,4,8,10,10s) is skewed and two channel joins/subscriptions are outstanding until the next flap self-heals it.
- Fix: Give each connection attempt a monotonically increasing generation/epoch (bump it in openSocket()/teardown()), capture it in the receiveTask closure, and have join() and the top of receiveLoop() bail out early if the captured epoch no longer matches `self`'s current epoch (in addition to the existing `stopped`/`socket` checks) — the same pattern MapModel already uses for `loadGeneration` to guard out-of-order loads.

## [3] Reminders.parseTime silently mis-schedules "Midnight"-labeled events (falls back to noon)
- **CONFIRMED** sev=medium  `Hygge/Backend/Reminders.swift:61`  domain=domain-api
- Description: DateHelpers.minutesOf(_:) explicitly special-cases the free-text values "noon" and "midnight" (DateHelpers.swift lines 74-75), and the app's own display code (ActivitiesView.swift ~L375) acknowledges that start_time can be arbitrary human text like "Sunset"/"TBD"/"Noon" rather than always the app-generated "h:mm a" format. Reminders.parseTime(_:) (Reminders.swift lines 61-77), used by fireDate(date:startTime:) (line 49-58), has no such handling: it only strips the substrings "am"/"pm" and looks for a leading integer. For the string "Midnight", isPM/isAM are both false, the digit-only parse fails (no digits present), parseTime returns nil, and fireDate falls through to its hardcoded default `comps.hour = 12; comps.minute = 0` (line 54) — i.e. it silently treats "Midnight" as noon.
- Failure: An event has event_date = "2026-12-31" and start_time = "Midnight" (a natural label for e.g. a New Year's countdown). A user requests a reminder at 3pm on 2026-12-31. fireDate computes fire = 2026-12-31 12:00 − 45m = 11:15am, which is already in the past relative to the 3pm request, so the `fire > Date()` guard in schedule(...) (line 26) is false and schedule() silently no-ops — no notification is ever registered, even though the real midnight event is still hours away. In other cases (earlier in the day) the reminder would fire ~11h15m before the real start instead of 45 minutes before it, both silently wrong with no error surfaced to the user.
- Fix: Route Reminders' time parsing through DateHelpers.minutesOf(_:) (or otherwise special-case "noon"/"midnight") instead of maintaining a second, less-capable parser in parseTime, so both call sites agree on what a given start_time string means.

## [4] confidentPhoto cache key omits coordinate — shared venue-name strings leak a wrong-venue confidence result
- **CONFIRMED** sev=medium  `Hygge/Backend/GooglePlacesService.swift:237`  domain=services
- Description: `confidentPhotoCache` (declared line 73) is keyed by `name` alone. `confidentPhoto(forFreeText:hint:)` (lines 222-226), used by `VenuePhoto` for events/clubs/trails, always resolves `coord` from `KnownVenues.coordinate(for: title + hint)` — i.e. the actual coordinate checked can differ per call even when `title` (the cache key) is identical, because `hint` (the event/club title, per ActivitiesView.swift:481-482/506-507, or trail.location, per TrailsListView.swift:219) varies. `confidentPhoto(name:coordinate:)` (lines 236-249) checks/writes the cache purely on `name`, so a second call with the same `name` but a different `coordinate` returns the FIRST call's cached result without ever re-running `isConfidentMatch`'s 75 m + name-align check against its own coordinate.
- Failure: Two clubs both list `location = "Community Room"` (a generic, reused venue label) but have different titles: Club A "Millstream Cleanup Crew" and Club B "Northland Nature Group". Rendering Club A first resolves KnownVenues → Millstream Park's coordinate, runs `confidentPhoto(name: "Community Room", coordinate: Millstream)`, and caches the outcome under key "Community Room". Rendering Club B resolves KnownVenues → Northland Park's coordinate, but `confidentPhoto(name: "Community Room", coordinate: Northland)` hits the cache from Club A and returns its Millstream-anchored result unchanged — Club B's card can end up displaying Millstream Park's photo (wrong venue) or wrongly showing a blank slot when its own Northland match would have passed, silently breaking Locked Rule A's per-venue geographic confidence guarantee.
- Fix: Key `confidentPhotoCache` on a composite of name + coordinate (e.g. "\(name)|\(coordinate.latitude),\(coordinate.longitude)"), or cache by the resolved place_id after the search step instead of the free-text venue name.

## [5] CalendarExport.addDay swallows per-event save failures and still reports success once one event lands
- **CONFIRMED** sev=low  `Hygge/Backend/CalendarExport.swift:55`  domain=services
- Description: In `addDay`, each event's `store.save(...)` error is discarded via `try?` (line 55) and only tallied into `written`; the function only throws `.saveFailed` when `written == 0` (line 58). Any events that individually fail to save (while at least one other succeeds) are dropped with no error signal at all.
- Failure: A day has 5 events; EventKit rejects 2 of them (e.g. a calendar-specific validation error) while 3 succeed. `addDay` returns `3` without throwing. `CalendarView.swift:621` calls this inside `InlineAction`'s `perform:` and discards the returned count; `InlineAction`'s doc-documented behavior is to go terminal on any non-throwing completion ("the UI keeps the action terminal after success so a day isn't added twice"), so the user sees "Added to your calendar" even though 2 of the 5 events were never written, and the action can never be retried for that day.
- Fix: Have `addDay` communicate partial failure (e.g. return `(written, total)` or throw a `.partialFailure(written:total:)` case) and have the calendar UI reflect a partial-success state instead of collapsing any `written > 0` into the same terminal success as a full success.

## [6] GooglePlacesService caches have no in-flight de-duplication, undermining the file's own cost-discipline goal
- **CONFIRMED** sev=low  `Hygge/Backend/GooglePlacesService.swift:128`  domain=services
- Description: `detailsCache`, `searchCache`, and `confidentPhotoCache` all follow "check cache → await network → write cache" (e.g. lines 128-160 for `details`, 171-198 for `search`, 237-249 for `confidentPhoto`) with no tracking of an already-in-flight request for the same key. Concurrent callers for the same key all observe an empty cache before the first one finishes and writes back.
- Failure: ActivitiesView renders several event/club cards that share the same `location` (e.g. multiple events at "Trailhead"). Each card's `VenuePhoto.task` fires `confidentPhoto(forFreeText:)` concurrently on first appear; every one of them reads the empty `confidentPhotoCache` entry before any completes, so N separate billed Places Text Search + Places Details requests fire for what should be one request — directly contradicting the header comment's stated design ("details are cached hard by place_id (the main spend lever)", "cost discipline… keep it frugal").
- Fix: Store an in-flight `Task<Result, Never>` per cache key and have concurrent callers await the same task instead of independently issuing new network requests.

## [8] Live-glow / 'Now' badges go stale because nothing drives a re-render off wall-clock time
- **CONFIRMED** sev=medium  `Hygge/Features/Map/SJMapView.swift:138`  domain=map-ui
- Description: `isLive(_:)` calls `DateHelpers.isLiveNow($0.startTime)` (default `now: Int = nowMinutes()`), but this is only re-evaluated when SwiftUI happens to re-run `annotations`/`body`, which only happens on an @State/@Published change (camera move, pin tap, filter change, or a MapModel realtime resync). There is no Timer/TimelineView anywhere in the codebase (confirmed via `grep -rn "Timer\|TimelineView"` across Hygge/) driving periodic re-evaluation purely because time has passed. The same mechanism affects MapSheet.swift:228 (`TodayEventRow(... live: DateHelpers.isLiveNow(ev.startTime))`) and MapSheet.swift:241 (`PlaceRow`'s `liveCount`).
- Failure: A neighbor opens the Map tab at 9:55 AM for a 10:00 AM parade already present in `todayEvents`, and just watches the screen without touching it. At 10:00:00 the pin should start pulsing coral and MapSheet's Today row should show a coral 'Now' badge (per the documented rule 'start ≤ now ≤ start+2h'), but since no state changed at that instant nothing re-renders, so the UI stays static (no glow) past the actual start time. Symmetrically, once `start+120min` passes while the tab stays open and idle, the pulse/badge keeps showing 'Now' indefinitely instead of turning off, until an unrelated interaction (pan/tap/foreground) happens to force a re-render.
- Fix: Drive a lightweight periodic re-render while the map is visible — e.g. a `TimelineView(.periodic(from: .now, by: 60))` wrapping the annotations/sheet content, or a MapModel-owned 60s Task loop that touches a `@Published` tick value — so `isLiveNow` is re-evaluated at least once a minute even with no data change.

## [9] Optimistic RSVP can be silently reverted by a concurrent load()
- **CONFIRMED** sev=medium  `Hygge/Features/Home/HomeModel.swift:68`  domain=home-ui
- Description: toggleRsvp() optimistically mutates today[i] and then awaits the network write. Its `catch` block explicitly re-resolves the row by id because 'a concurrent load() may have replaced `today`' — but the success path (the `do` block's happy path, lines 74-76) has no such re-sync. If a concurrent load() (e.g. pull-to-refresh, or the .task firing again) replaces the whole `today` array with a server snapshot taken before this RSVP write lands, and the write then succeeds, nothing re-applies the optimistic rsvpd/goingCount onto the new array — the UI is left showing the pre-toggle state even though the RSVP genuinely succeeded server-side.
- Failure: 1) Home tab loads today = [event e1 (rsvpd:false, goingCount:0)]. 2) User taps RSVP on e1: toggleRsvp sets today[0].rsvpd=true, goingCount=1, weekGoing+=1, then awaits api.rsvpEvent(e1) (in flight). 3) Before that POST commits, the user pulls-to-refresh, which calls model.load(api) concurrently; its GET for today's events lands before the RSVP POST has committed on the server, so it returns e1 still rsvpd:false/goingCount:0 and overwrites `today` wholesale. 4) The original rsvpEvent(e1) POST then succeeds — the do block's success path does nothing further, so the UI keeps showing 'RSVP'/rsvpd:false for e1 even though the user is actually RSVP'd server-side, until the next full reload (e.g. leaving and returning to the Home tab, which recreates HomeModel from scratch).
- Fix: On the success path of toggleRsvp, re-resolve the row by id the same way the catch block does (or simply skip re-applying if the array was replaced), e.g. after the await succeeds, look up `today.firstIndex(where: { $0.id == ev.id })` and ensure rsvpd/goingCount reflect `!wasGoing` regardless of whether a concurrent load() replaced the array in the meantime.

## [10] RollCallSection and QuestSection show a false empty/zero state on every Home-tab revisit, unlike the Today section which has a loading guard
- **CONFIRMED** sev=low  `Hygge/Features/Home/HomeView.swift:59`  domain=home-ui
- Description: MainTabsView (Hygge/App/RootView.swift, the `switch tab { case .home: HomeView(...) }` inside a Group) only instantiates the currently-selected tab's view — HomeView (and its @StateObject HomeModel) is torn down and recreated every time the user navigates away from and back to the Today tab. HomeView's own `todaySection` guards on `model.loading && !model.loaded` to show a `TodayLoadingCard` skeleton instead of the real empty state while data is in flight (HomeView.swift lines 95-98). But `RollCallSection(count: model.weekGoing)` (line 59) and `QuestSection(quest: model.quest, ...)` (line 63) are rendered unconditionally with HomeModel's default init values (weekGoing = 0, quest = nil) and have no equivalent loading gate, so on every return to the Today tab they briefly assert 'Quiet week in St. Joe' / 'Nothing on the board yet this week' and 'A small nudge each day' (no quest) before the real (possibly nonzero / present) data arrives from load().
- Failure: Town has an active week (weekGoing > 0) and today's quest is set. User is on the Map tab, switches to the Today tab (or backgrounds/foregrounds causing a tab remount, or simply the first cold launch). Because HomeModel is freshly constructed with weekGoing=0/quest=nil and the network fetch in load() hasn't resolved yet, RollCallSection renders 'Quiet week in St. Joe — Nothing on the board yet this week' and QuestSection renders the no-quest placeholder for a frame or two, i.e. the UI momentarily states something false about real town activity, then flips to the correct values once load() completes — every single time the user navigates back to Today, not just on first app launch.
- Fix: Gate RollCallSection and QuestSection the same way todaySection is gated (e.g. show their existing skeleton-style placeholders, or simply hold rendering until `model.loaded` is true) so a fresh HomeModel never asserts 'quiet week' / 'no quest' before the first fetch has actually resolved.

## [11] Explore feed silently rebrands network failures as "nothing here yet"
- **CONFIRMED** sev=medium  `Hygge/Features/Activities/ActivitiesModel.swift:17`  domain=explore-cal-ui
- Description: ActivitiesModel.load() has no `failed` flag (unlike its sibling CalendarModel, whose own doc comment states the house rule: "a failed load ... never masquerades as empty — the view gets an explicit failed / dayFailed"). Here, any thrown error from getApprovedClubs()/getTrails()/getUpcomingEvents() is caught and discarded (`// calm empty state on error`), then `loaded = true` is set unconditionally. ActivitiesView only branches on `model.loading`/`model.loaded` (lines 110-115, 268-283) and has no offline/failed state, so a genuine fetch failure renders exactly like a legitimately empty town: "Nothing here yet — real clubs, events, and trails show up here once neighbors post them."
- Failure: User opens the Explore tab with a flaky connection (e.g. one bar of LTE, momentary Wi-Fi drop, or the .task getting cancelled by a quick tab-switch away and back). getApprovedClubs() throws a URLError (not an auth failure, so AuthStore does not route to Login). The catch block swallows it, loaded flips to true, and the user is shown the calm empty state implying St. Joseph has no clubs/events/trails at all, with no way to tell this apart from a real outage and no retry affordance beyond an unlabeled pull-to-refresh.
- Fix: Add a `@Published var failed = false` to ActivitiesModel mirroring CalendarModel's discipline: set it in the catch block only when there is nothing already loaded, clear it on success, and have ActivitiesView show the same quiet "Couldn't reach ..." copy CalendarView already uses for this exact situation.

## [12] Club join/leave has no in-flight guard — out-of-order requests can leave local state opposite the server
- **CONFIRMED** sev=medium  `Hygge/Features/Activities/ActivitiesModel.swift:30`  domain=explore-cal-ui
- Description: toggleJoin() fires-and-forgets a single POST (join) or DELETE (leave) per tap with no per-club in-flight token and no button-disable while a request is outstanding (ClubExploreCard in ActivitiesView.swift, lines 508-517, calls `Task { await model.toggleJoin(api, c) }` on every tap unconditionally). If a user taps Join then quickly taps again to Leave (a natural double-tap-to-undo gesture, not a pathological one), two independent async requests (POST upsert then DELETE) are in flight concurrently with no ordering guarantee between them.
- Failure: t=0: tap Join — optimistic UI sets joined=true, memberCount+1, fires POST club_members (upsert). t=0.3s (after SwiftUI re-renders with joined=true): tap again to leave — optimistic UI sets joined=false, memberCount-1, fires DELETE club_members. If the DELETE reaches PostgREST and completes before the still-in-flight POST (plausible under retry/backoff or connection reuse jitter), the final server row is INSERTed after the DELETE, so the club_members row persists (user is actually a member) while the local UI shows "not joined" and a member count uninflated by one — wrong until the next full model.load(). This directly contradicts the "real data only — never seeded/inflated counts" rule since the displayed count is now stale/incorrect indefinitely.
- Fix: Track an in-flight club id (or disable the join button while its own request is outstanding) so a second tap either no-ops or cancels/supersedes the first request before firing the opposite one, similar to CalendarModel.loadDay's `dayRequest` token pattern.

## [13] Explore feed uses a plain VStack (not lazy) so every card — and every trail's geocode network call — renders/fires eagerly on load
- **CONFIRMED** sev=medium  `Hygge/Features/Activities/ActivitiesView.swift:104`  domain=explore-cal-ui
- Description: Both the outer scroll content (`explore`, lines 104-119) and the `feed` view (lines 241-266) build their card lists inside a plain `VStack`, not a `LazyVStack`, inside a `ScrollView`. SwiftUI constructs every child of a non-lazy VStack immediately regardless of scroll position. Each TrailExploreCard's `.task` (lines 550-552) unconditionally calls `GeocoderService.shared.coordinate(for:)` (a live network geocode against Google Places / Nominatim) the moment its view is built — so every trail in the current filter, not just the ones on-screen, issues a geocode request on every load/refresh/filter change. Calendar's equivalent scroll views (CalendarView.swift monthScroll/agenda) correctly use LazyVStack, underscoring this is an inconsistency rather than a deliberate choice.
- Failure: St. Joseph's Explore tab grows to a realistic community size (e.g. 40 clubs + 25 community trails + 100+ upcoming events during festival season) and a user opens the "All" filter or pulls to refresh: the VStack instantiates all ~165 cards at once (defeating ScrollView virtualization and causing visible jank/scroll-stutter), and roughly 25 concurrent geocoding HTTP calls fire simultaneously for off-screen trail cards the user hasn't scrolled to yet — wasted network/rate-limit pressure on Nominatim's public, rate-limited endpoint (which explicitly requires a courteous request rate per its usage policy) purely because the cards were built eagerly rather than on appearance.
- Fix: Swap the outer content VStack and `feed`'s VStack for LazyVStack (matching CalendarView's pattern) so off-screen cards — and their `.task`-driven geocode calls — only materialize once scrolled into view.

## [14] Onboarding/profile hydration is device-session-scoped, not per-user — a second account on the same device permanently skips onboarding and inherits the previous user's local identity mirror
- **CONFIRMED** sev=high  `Hygge/App/RootView.swift:88`  domain=flow-ui

# TOPIC: Codebase architecture, concurrency, testability, tech debt

### [priority=high|effort=M] Give AuthStore/CommunityAPI a protocol seam so features are unit-testable without the network
- concern: Every feature Model instantiates CommunityAPI directly against AuthStore.shared (or an injected concrete AuthStore), so there is no way to unit-test HomeModel.load(), ActivitiesModel.toggleJoin(), CalendarModel.load()/loadDay(), etc. without a live Supabase project and a real signed-in session.
- now: CommunityAPI (Hygge/Backend/CommunityAPI.swift:20-22) is `struct CommunityAPI { let auth: AuthStore }` — good instinct (it's a value type taking a dependency, not itself a singleton) — but `AuthStore` is a concrete `@MainActor final class` with no protocol, and every call site does `private var api: CommunityAPI { CommunityAPI(auth: auth) }` where `auth` is an `@EnvironmentObject`/`@ObservedObject` bound to `AuthStore.shared` (e.g. Hygge/Features/Home/HomeView.swift:24, Hygge/Features/Activities/ActivitiesView.swift:55, Hygge/Features/Calendar/CalendarView.swift:29, Hygge/Features/Map/QuickAddSheet.swift:31, Hygge/Features/Profile/ProfileModel.swift:34). `CommunityAPI.token()` calls `auth.validAccessToken()` directly (CommunityAPI.swift:27), so any call into the API requires a real AuthStore with Keychain state.
- proposal: Extract a minimal `protocol TokenProviding { func validAccessToken() async throws -> String; var userId: String? { get }; var email: String? { get } }`, have `AuthStore` conform, and change `CommunityAPI.auth` to hold that protocol type instead of the concrete class. Add a fake `TokenProviding` in a small `HyggeTests` target for model-level tests. This is a type change, not a rewrite — every call site keeps passing `AuthStore.shared`/`auth`, they just now satisfy a protocol.
- why: This is the single seam that currently blocks testing the whole Model layer (6 Model files: HomeModel, CalendarModel, MapModel, AddModel, ProfileModel, ActivitiesModel all funnel through `CommunityAPI(auth:)`). Doing it now, while CommunityAPI is still one file, is far cheaper than retrofitting once more call sites and features exist. It doesn't touch RLS or add an SDK — purely a Swift-side seam.

### [priority=high|effort=S] Stand up a minimal XCTest target and start with DateHelpers + RealtimeClient reducer
- concern: There is no XCTest target at all (confirmed no test scheme). The two highest-risk pieces of logic in the app — timezone-correct date math and the realtime-relevance reducer — are pure enough to test today but are only ever checked by screenshot.
- now: `DateHelpers` (Hygge/Backend/DateHelpers.swift) is a stateless `enum` of pure functions: `localDate`, `addDays`, `prettyDate`, `weekdayLabel`, `daysBetween`, `minutesOf` (free-text time parsing via regex), `nowMinutes`, `isLiveNow`. `isLiveNow` (line 100-105) is the exact rule CLAUDE.md calls out as brand-critical ("Coral is reserved for live/tappable") and it's a 6-line pure function with zero test coverage. Separately, `MapModel.handle(_:)` (Hygge/Features/Map/MapModel.swift:144-166) is a pure reducer over `RealtimeClient.Change` → `Bool` (`touchesToday`/`currentlyShown`/relevance-by-kind) deciding whether a websocket event triggers a re-fetch; it's already isolated from the socket and directly testable if the logic were exposed as a free function for injection of synthetic `Change` values.
- proposal: Add an `HyggeTests` XCTest target (Debug-only, not shipped). Phase 1: pure-function tests for `DateHelpers` (`isLiveNow` boundary at start/start+120, `minutesOf` for "7am"/"noon"/"midnight"/malformed, DST-adjacent `localDate`/`daysBetween`). Phase 2: extract `MapModel`'s `handle`/`touchesToday`/`currentlyShown` logic into a free function or small `RealtimeRelevance` struct so it can be tested against synthetic INSERT/UPDATE/DELETE `Change` values without a socket. Phase 3: decoding tests for `Models.swift`'s `Codable` structs against fixture JSON (catches a silent PostgREST column-rename before it reaches the simulator). Explicitly skip network/AuthStore-dependent tests until the protocol seam above lands.
- why: This is the most surgical, highest-value first slice: these functions are pure, already isolated, and guard the two things CLAUDE.md repeatedly calls out as correctness-critical (timezone dates, live-glow, DELETE-by-id matching). It gives a real regression net for the parts of the app most prone to silent logic drift, without any architecture change or violating "no supabase-swift SDK"/"builds clean + screenshot" discipline — it's purely additive.

### [priority=high|effort=S] Add a single, brand-safe error/observability hook instead of the current silent-swallow-everywhere pattern
- concern: There is zero logging in the entire app — no print, os_log, Logger, or NSLog anywhere in Hygge/ — and the large majority of catch blocks are empty or comment-only ("calm empty state on error", "Leave whatever we have; the UI shows calm empty states"). That's a deliberate, on-brand UX choice for the user, but it leaves the developer with no way to know a decode broke, a table got renamed, or RLS started rejecting a query, short of noticing an unexpectedly-empty screen during a manual screenshot pass.
- now: Confirmed via full-repo search: 0 hits for print/os_log/Logger/NSLog across Hygge/. Representative empty catches: HomeModel.swift:43-45 (today/quest fetch), HomeModel.swift:60-62 (board fetch), ActivitiesModel.swift:23-25 (clubs/trails/events), CalendarModel.swift:59-62 (month range). Only a few call sites (AddModel.swift:122-123, QuickAddSheet.swift:161-162) surface `(error as? SupabaseError)?.message` to the user, and only for write actions — reads are silent everywhere. `SupabaseError` (SupabaseHTTP.swift:11-15) already carries a structured `message` + `status`, so the information exists at the throw site; it's simply discarded at every read-path catch.
- proposal: Add one small, dependency-free helper (e.g. Hygge/Support/Log.swift) built on Apple's built-in `os.Logger` — no new SPM dependency, no third-party analytics SDK, so it doesn't violate the "no notification-spam / real-data-only" brand constraint or the hand-rolled-backend rule — with a couple of subsystem categories (.network, .realtime, .auth). Call it from the existing empty catch blocks, one line each (e.g. `Log.network.error("HomeModel.load today: \(error)")`), without changing any UI behavior — the calm empty state still renders. Purely additive: it surfaces in Console.app / Xcode's device log during a simulator run or a tethered TestFlight session, with zero user-facing or backend footprint.
- why: Right now a broken query and an honestly-empty table are visually and diagnostically identical, which will make the first production bug report ("the calendar is empty for me") unnecessarily hard to triage. os.Logger respects the calm-brand constraint (no telemetry SDK, no network calls, no user-visible surface) while giving a real trail during a debug session or log collection.

### [priority=medium|effort=M] Unify the five ad-hoc LoadState shapes into one shared type
- concern: Every feature Model reinvents its own loading/error vocabulary, so the same conceptual state (loading / loaded-with-data / loaded-empty / failed-with-nothing / stale-but-shown) is spelled differently everywhere, and the staleness/retry discipline CalendarModel and MapModel are careful about is easy to forget in the next feature.
- now: MapModel has a real `enum LoadState: Equatable { case loading, loaded, empty, error, offline }` (MapModel.swift:21) — the most complete model. HomeModel instead uses two independent `@Published var loading`/`loaded` Bools plus a separately-shaped `TodayInStJoeContent` enum for the board (HomeModel.swift:12,18-19). ActivitiesModel duplicates the same `loading`/`loaded` Bool pair with no error flag at all (ActivitiesModel.swift:14-15) — a failed `getApprovedClubs()`/`getTrails()`/`getUpcomingEvents()` in `load()` (lines 19-25) falls straight through to empty arrays with a comment ("calm empty state on error") and gives the view no way to distinguish "actually empty" from "fetch failed." CalendarModel invents yet another shape: `loaded`/`failed` for the month view plus a second, parallel `loadingDay`/`dayFailed` pair for the day sheet (CalendarModel.swift:20-25).
- proposal: Promote MapModel's `LoadState` (or a variant with an associated value distinguishing "loaded-with-data" from "loaded-empty") to a shared type in e.g. Hygge/Backend/LoadState.swift, and migrate HomeModel, ActivitiesModel, and CalendarModel's independent state pairs onto it one Model at a time, each a self-contained diff.
- why: Five slightly different encodings of the same four/five states is real duplication (the project's own graph even surfaces "LoadState" and "Session & Load-State Models" as a distinct community, suggesting this was already half-noticed). A shared type also closes the ActivitiesModel gap where a real fetch failure is currently indistinguishable from "no clubs/trails/events exist" — which cuts against the "real data only" ethos in spirit, since an outage silently masquerades as an honest empty state instead of surfacing as "couldn't load."

### [priority=medium|effort=S] Break up the two largest Views (ActivitiesView, CalendarView) before they grow further
- concern: The View+Model house pattern (View owns layout, Model owns state+API) is followed consistently, but two Views have grown past the point where a single file is easy to reason about or safely change, and they're exactly the screens likely to keep growing.
- now: ActivitiesView.swift is 658 lines and CalendarView.swift is 631 lines — the two largest files in the codebase (vs. the next-largest, CommunityAPI.swift at 547, and the Map feature's SJMapView.swift/MapSheet.swift at 466/453, which are already split into two cooperating files despite being the most complex feature overall). Both single-file Views mix top-level layout, filter-chip chrome, per-row card composition, and sheet presentation, and both back a wide DEBUG launch-arg surface (-explore-filter, -explore-timeframe, -calendar-face, -calendar-open, -calendar-legend per CLAUDE.md) that targets sub-states all living in the same file.

Pure extraction of existing `some View` sub-builders into their own files/structs, no behavior change, verified with the existing DEBUG launch-arg screenshot flow.
- why: Splitting now, while the two files are internally still one coherent screen each, is a small mechanical diff; waiting until a third sub-feature (e.g. a new Activities filter or Calendar view mode) gets bolted on makes the eventual split riskier and larger.

### [priority=low|effort=S] Fold the growing .shared singleton pattern into the same DI pass as AuthStore/CommunityAPI

- now: There is no `supabase/` directory, no `.sql` files, and no migrations folder anywhere in this repo (verified: `find . -iname '*.sql'` and `find . -iname '*migration*'` both return nothing). CLAUDE.md itself documents the practice: MAP_BUILD_LOG.md's "SQL — already applied to the live project `lxdgwhvqjqmqliobwjpi` (via MCP)" section (line 238) shows `alter publication supabase_realtime add table public.club_events;` and `alter table public.club_events replica identity full;` run directly against production, with the log entry as the only record. The same pattern repeats later in the file for the new `town_profiles` table + RLS, the `avatars` storage bucket, and a `board_items_dedup_unique_index` (lines 508-539) — each described in prose, none captured as a runnable, diffable migration. `SupabaseHTTP.swift`/`CommunityAPI.swift` assume specific columns and constraints (e.g. `on_conflict=user_id`, `on_conflict=club_id,user_id`) exist, but nothing in-repo proves it.
- proposal: Adopt the Supabase CLI's migrations workflow (`supabase migration new`, `supabase db diff`) purely as a source-of-truth log: every schema/RLS/publication change gets a numbered `.sql` file committed alongside the Swift change that depends on it, applied via `mcp__*__apply_migration` or the CLI instead of ad hoc `execute_sql`. Keep MAP_BUILD_LOG.md as the narrative layer (it's valuable) but stop treating it as the durable record — the migrations directory becomes that. This does not require self-hosting or a local Postgres; it's just "commit the SQL you already write."
- why: This is the single highest-leverage foundation: it de-risks every other recommendation below (twin sync, RLS enforcement, recurrence modeling) by making schema state auditable and reproducible instead of tribal knowledge living in one person's MCP session history. It costs almost nothing on top of work already being done (the SQL is already being written and pasted into the log) — it just needs a `git commit` destination.

### [priority=high|effort=M] Close the client-side status-authorization gap before content volume grows
- concern: Whether a submitted event/club is auto-published (`status='approved'`) or queued is decided entirely by client-side Swift, not enforced by RLS — so any authenticated user, not just the intended admin, can bypass moderation by talking to PostgREST directly, and the pending queue nothing actually drains has no admin UI to review it.
- now: `CommunityAPI.submitClub` (line 97): `let status: ClubStatus = Admin.isAdmin(auth.email) ? .approved : .pending` — a client-side branch. `AddModel.swift` similarly sets `status = queued ? .pending : .approved` where `queued` comes from `Moderation.check` (`Moderation.swift`), which fails open to the queue sentinel on any transport error. MAP_BUILD_LOG.md (line 256) confirms the actual DB policy: "the existing `submit events` INSERT policy is `with_check (submitted_by = auth.uid())` with no status constraint" — i.e. RLS does not distinguish admin from non-admin, or moderated from unmoderated, for the `status` column. Separately, `graphify-out/REVIEW_DIGEST.md` finding #4 confirms `getPendingPosts/getPendingClubs/approvePost/rejectPost/setClubStatus` (`CommunityAPI.swift:475-499`) have zero callers anywhere in the app — there is no review screen, so any row that *does* land as `pending` is invisible forever without manual SQL.
- proposal: Two independent, additive fixes, neither a rewrite: (1) add a Postgres trigger or RLS `with_check` clause that forces `status='pending'` on INSERT unless `auth.email()` is in an admin allowlist maintained in SQL (mirroring `Admin.isAdmin`), so self-approval is a real server-side guarantee, not a UI convention; (2) either ship the minimal admin "Pending" review screen the API already fully supports (it's dead code waiting for a view), or — if the product decision is "nothing gets held" at current town-sized scale — remove the pending/queue language from `AddModel`'s UI copy so users aren't told about a channel that doesn't exist.
- why: At today's trusted-small-town scale this gap is low-consequence, but the task explicitly asks for moderation-at-scale foundations, and the current design has no floor: nothing stops a bad actor from self-approving spam directly against PostgREST, and nothing surfaces the pending rows that do accumulate. Fixing this now (while the schema/RLS is small and the review-digest already did the discovery work) is far cheaper than retrofitting it once submission volume grows.

### [priority=high|effort=S] Give the two-repo "backend twin" a real sync mechanism, not a comment
- concern: Data that must stay identical across this repo and the separate Expo repo (curated venue coordinates, the admin email, the real-only submission filter) is kept in sync purely by a doc-comment promise, and drift has already happened once inside this repo alone.
- now: `KnownVenues.swift`'s header states outright: "Mirrors `apps/mobile/src/lib/geo.ts` in the Expo repo — keep the two tables in sync when adding a venue" (lines 9-10) — there is no shared file, generator, or CI check, just a comment read only by whoever edits next. `graphify-out/REVIEW_DIGEST.md` finding #5 shows this class of drift is not hypothetical: a corrected Lake Wobegon trailhead coordinate propagated to `TrailsMapView`, `KnownVenues.swift:38`, and `MapSpots.swift:63` but was missed in `TrailsListView.swift:103` and `ActivitiesView.swift:582` — three of five in-repo copies got the fix, two didn't, sending Directions ~700 m off. `Admin.defaultEmail` (`DateHelpers.swift:110`) is the same pattern at smaller scale (mirrors `DEFAULT_ADMIN_EMAIL` in `@hygge/core`).
- proposal: Don't build a cross-repo package (too heavy for two apps of this size). Instead: (1) within this repo, collapse the venue-coordinate duplication first — `TrailsListView`/`ActivitiesView`'s local literals should call `KnownVenues.coordinate(for:)` like `TrailsMapView` already does, eliminating the in-repo half of the drift risk in one small change; (2) for the actual cross-repo half, add one JSON file (e.g. `shared/known-venues.json`) that both repos import/parse at build or content-authoring time, generated from whichever repo edits it first, with a short script that diffs the other repo's copy and fails CI/warns if they've diverged — cheaper than a shared package, but no longer relies on a comment being read.
- why: The failure mode here isn't hypothetical — it already occurred and was only caught by a manual review pass, not by any automated check. As the real-St.-Joe content pipeline scales (more venues, more recurring series), the number of places a coordinate/id/threshold needs to match across two codebases will only grow, and "keep in sync" comments don't scale with headcount of one.

### [priority=medium|effort=M] Add a minimal last-good-snapshot cache for the core screens
- concern: The app has no offline/caching story at all beyond the auth session and onboarding interests — every screen re-fetches from PostgREST on each appearance, so a dead-zone moment (a real condition in and around a small MN town) shows an empty/error state instead of the data the user saw five minutes ago.
- now: Confirmed via search: no `URLCache` configuration, no `NWPathMonitor`/reachability, no CoreData/SwiftData, no on-disk cache of events/board/calendar data anywhere in `Hygge/`. "Offline" is only handled as a terminal UI state — `MapModel.LoadState.offline` (`MapModel.swift:21`, set when `error is URLError`) and `CalendarView.offlineNote` (`CalendarView.swift:223`) — that tells the user nothing loaded, rather than showing stale-but-useful data. The only things that do survive offline are the Keychain-persisted `Session` (`AuthStore.swift`) and `UserDefaults`-persisted interests/name (`Interests.swift`), by explicit design (`ProfileModel.swift:58`'s "instant first paint from local mirrors" comment shows the pattern already exists for profile identity, just not for content).
- proposal: Extend the same "local mirror, refine from network" pattern `ProfileModel` already uses to the map's today-events, the board sections, and the calendar's current-month agenda: cache the last successful decode for each to a small JSON file (or just `UserDefaults` for the today/board payloads, which are small), show it immediately on load, and only fall back to the existing offline/error UI when there is no cached data at all yet. No new dependency, no sync engine — just "remember the last good response."
- why: This is squarely a foundation-not-rewrite: the pattern already exists in one place (`ProfileModel`) and just needs to be generalized. For an app whose core value is "what's happening today" and a live map, showing nothing during a connectivity blip is the worst possible failure mode for the calm-and-reliable brand promise, and it's cheap to fix incrementally per-screen rather than all at once.

### [priority=medium|effort=M] Model recurring events as a recurrence, not N duplicate rows
- concern: Recurring content (farmers market Fridays, weekly trivia, club meetups) is stored as one literal `club_events` row per occurrence and reassembled into "Every Tuesday" cards at read time — a pattern that doesn't scale cleanly as the real-content pipeline grows and has already produced a duplicate-insert bug.
- now: MAP_BUILD_LOG.md's content-pipeline entry (line 513-524) describes the pattern directly: "Recurring rows collapse to clean 'Every Tuesday/Wednesday/Friday' cards via `groupRecurring`" — i.e. the DB holds N discrete rows per series and the client groups them for display. `graphify-out/REVIEW_DIGEST.md` finding #15 shows this already caused a real bug: `AddModel.swift:97`'s weekly-repeat submission does N sequential unguarded inserts with no idempotency key, so a mid-loop failure + retry duplicates weeks.
- proposal: Add a nullable `recurrence_rule` (a simple weekday+cadence string, not full RRULE) and `series_id` to `club_events`, insert one canonical row per series instead of N, and expand occurrences at read time in `CommunityAPI` (where `groupRecurring`-style logic already partially exists) or via a Postgres view. This is additive — existing single-occurrence rows keep working with `recurrence_rule = null`.
- why: The current model means editing a recurring series' time requires updating every already-inserted occurrence, unbounded row growth as more recurring series are added (church schedules, farmers market, weekly clubs are exactly the kind of real content this app is built to carry), and a live duplicate-insert bug on retry. Fixing the data model now, while the row count is still small (46 events per the last content pass), is far cheaper than a migration once there are hundreds of historical occurrence-rows to reconcile.

### [priority=medium|effort=S] Add a server-side kill switch and minimal ops visibility — no analytics SDK
- concern: There is zero feature-flagging and zero telemetry/crash-reporting of any kind, so a bad realtime/map change ships instantly to the whole town with no staged rollout, no kill switch, and no way to know in production whether something silently broke for a subset of users.
- now: Confirmed via search: no `FeatureFlag`/`RemoteConfig` type anywhere, no `Analytics`/`Mixpanel`/`Amplitude`/`Sentry`/`Crashlytics` reference anywhere, and the only SPM dependency is `mapbox-maps-ios` (per `Hygge.xcodeproj`). "Verified" per CLAUDE.md means manual screenshot review in the simulator — there is no automated signal from real devices once shipped. Given `MapModel` pushes realtime `club_events` changes to every subscribed client instantly (`RealtimeClient.swift`) and admin-approved events go live app-wide with no staging step, a bad change has no brake.
- proposal: Nothing that resembles user tracking (respecting the calm-brand, real-data-only mandate): a single small `app_config` PostgREST table (public-read, admin-write RLS) holding a handful of booleans/strings — e.g. `realtime_enabled`, `min_supported_build` — read once at launch the same way `getEvergreenLine()` already reads a small config-shaped table today. Pair it with Apple's own `MetricKit` (on-device, no third-party SDK, no per-user tracking, aggregate crash/hang reports only) for basic "is production actually healthy" visibility — it ships with iOS and requires no new dependency or user consent flow.
- why: This isn't about growth analytics — it's about the operational floor a live-realtime feature needs before it's driving a bigger, more diverse install base than a handful of testers. Both pieces are additive, tiny, and match the hand-rolled-over-SDKs philosophy already used everywhere else in `Backend/`.

### [priority=low|effort=S] Harden Codable decoding against a single bad row blanking an entire screen
- concern: Every list-shaped PostgREST response decodes as `[RawStruct]` via `JSONDecoder` with no per-row fallback, and several "raw" structs (like `RawEvent.title`) have non-optional required fields — so one malformed row (a bad manual DB edit, a partially-applied migration, a future nullable column) fails decoding for the whole array, not just that row.
- now: `Models.swift`'s header states decoding relies purely on `.convertFromSnakeCase` (line 5) with no `CodingKeys` anywhere in the file for drift protection, and `RawEvent` (line 135) declares `title: String` non-optional while `CommunityAPI` decodes it in bulk (`let events: [RawEvent] = try decode(data)`, e.g. line 128). Given schema changes are applied directly against production via ad hoc SQL (see the schema-versioning finding above) rather than through a reviewed migration process, the risk of a stray null landing in a required column is not hypothetical.
- proposal: For the handful of list endpoints that drive the map/timeline/board (the screens the brand promise is built on), decode leniently: iterate the raw `[[String: Any]]`/`JSONSerialization` array and `try?`-decode each element individually, dropping only the bad row instead of throwing for the whole response. This is a small, local change to `CommunityAPI`'s `decode<T>` helper (an overload, not a rewrite) and doesn't touch the well-typed request/insert side.
- why: Lowest-priority item here, but cheap insurance given the app's own practice of hand-editing the live schema and content via direct SQL (MAP_BUILD_LOG.md's SQL-inserts-for-content-pass pattern) — a single bad row today already has the blast radius of "the whole map goes blank," and that blast radius only grows as more people (or automation) touch the live data.
